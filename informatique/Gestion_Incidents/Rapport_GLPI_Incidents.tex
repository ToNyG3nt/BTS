\section{Introduction}

L'objectif de ce TP est de mettre en place un mini helpdesk à partir de GLPI sur un environnement Debian avec la pile LAMP (Linux, Apache, MariaDB, PHP). Il s'agit de simuler le fonctionnement d'un service support informatique : installation de l'outil, création d'utilisateurs avec des rôles distincts, traitement de tickets d'incidents et de demandes, puis capitalisation des solutions dans une base de connaissances.

Ce compte rendu présente chaque étape réalisée, accompagnée de captures d'écran et des réponses aux questions posées.

\section{Exercice 1 -- Préparation de l'environnement de travail}

\subsection{Travail réalisé}

Avant d'installer GLPI, j'ai vérifié que la pile LAMP était opérationnelle sur Debian. Les services Apache et MariaDB ont été installés et activés :

\begin{lstlisting}[language=bash]

\subsection{Rôle de chaque composant}

\begin{description}
    \item[\textbf{Apache :}] Serveur web qui reçoit les requêtes HTTP du navigateur et sert les fichiers PHP de l'application GLPI.
    \item[\textbf{PHP :}] Langage de programmation côté serveur utilisé par GLPI pour générer les pages dynamiquement.
    \item[\textbf{MariaDB :}] Système de gestion de base de données qui stocke toutes les informations de GLPI (utilisateurs, tickets, matériel\ldots).
    \item[\textbf{Navigateur web :}] Interface cliente permettant d'accéder à GLPI via une adresse HTTP locale.
\end{description}

\begin{qabox}
\begin{description}
    \item[\textbf{Q1 -- Pourquoi GLPI a-t-il besoin d'un serveur web ?}]~\\
    GLPI est une application PHP : Apache interprète ce code côté serveur et renvoie les pages au navigateur.

    \item[\textbf{Q2 -- Quel est le rôle de la base de données dans un outil de ticketing ?}]~\\
    Elle conserve toutes les données de GLPI entre les sessions : utilisateurs, tickets, historiques et matériel inventorié.

    \item[\textbf{Q3 -- Pourquoi utilise-t-on un navigateur pour accéder à GLPI ?}]~\\
    GLPI génère son interface en HTML/CSS, donc n'importe quel navigateur suffit pour y accéder, sans logiciel à installer sur les postes.
\end{description}
\end{qabox}

\section{Exercice 2 -- Installation de GLPI}

\subsection{Installation des dépendances PHP}

GLPI nécessite plusieurs extensions PHP supplémentaires pour fonctionner :

\begin{lstlisting}[language=bash]
sudo apt install php-{apcu,cli,common,curl,gd,mysql,xml,mbstring,bcmath,intl,zip,bz2}
\end{lstlisting}

\subsection{Déploiement des fichiers GLPI}

J'ai téléchargé l'archive GLPI et extrait les fichiers dans le répertoire web :

\begin{lstlisting}[language=bash]
wget https://github.com/glpi-project/glpi/releases/download/10.0.x/glpi-10.0.x.tgz
sudo tar -xzvf glpi-10.0.x.tgz -C /var/www/html/
sudo chown -R www-data:www-data /var/www/html/glpi/
\end{lstlisting}

GRANT ALL PRIVILEGES ON glpi.* TO 'glpiuser'@'localhost';
FLUSH PRIVILEGES;
\end{lstlisting}

    \item[\textbf{Q1 -- Pourquoi créer un utilisateur MariaDB dédié plutôt qu'utiliser \texttt{root} ?}]~\\
    Un compte dédié limite les droits à la seule base \texttt{glpi}, ce qui réduit l'impact en cas de compromission de l'application.

    \item[\textbf{Q2 -- À quoi sert l'encodage \texttt{utf8mb4} ?}]~\\
    Il prend en charge la totalité des caractères Unicode (accents, emojis\ldots) sans risque de troncature ou d'erreur d'encodage.

    \item[\textbf{Q3 -- Différence entre installation TP local et installation de production ?}]~\\
    En TP on accepte un mot de passe simple et pas de HTTPS ; en production ces éléments sont obligatoires, accompagnés de sauvegardes régulières et d'une supervision.
\end{description}

\begin{description}
    \item[\textbf{Description :}] L'utilisateur \texttt{enseignant1} ne peut plus ouvrir sa session Windows. Le message d'erreur indique que les identifiants sont incorrects.
    \item[\textbf{Suivi technique :}] Vérification que le verrou Majuscules n'est pas activé. Test du compte sur un autre poste confirmant le blocage. Réinitialisation du mot de passe via le technicien.
    \item[\textbf{Statut :}] En cours -- ticket assigné à \texttt{technicien1}.

\subsubsection*{Ticket 4 -- Accès à une imprimante}
\begin{description}
    \item[\textbf{Description :}] L'utilisateur \texttt{enseignant1} demande l'accès à une imprimante réseau pour imprimer ses documents.
    \item[\textbf{Suivi technique :}] Identification de l'imprimante concernée. Ajout du compte utilisateur dans le groupe d'impression correspondant.
    \item[\textbf{Statut :}] En cours -- ticket assigné à \texttt{technicien1}.
\end{description}

\subsubsection*{Ticket 5 -- Installation d'un logiciel validé par le responsable}
\begin{description}
    \item[\textbf{Description :}] L'utilisateur \texttt{enseignant1} demande l'installation d'un logiciel sur son poste, après validation préalable du responsable.
    \item[\textbf{Suivi technique :}] Vérification de la validation dans la liste des logiciels autorisés. Téléchargement depuis la source officielle et installation sur le poste.
    \item[\textbf{Solution :}] Logiciel installé et fonctionnel. L'utilisateur a été informé.
    \item[\textbf{Statut :}] Résolu.
\end{description}

\begin{qabox}
\begin{description}
    \item[\textbf{Q1 -- Différence entre urgence, impact et priorité ?}]~\\
    L'urgence vient du ressenti de l'utilisateur, l'impact mesure le nombre de personnes touchées ; GLPI combine les deux pour calculer automatiquement la priorité.

    \item[\textbf{Q2 -- Pourquoi le Wi-Fi en salle est plus prioritaire qu'une installation logicielle ?}]~\\
    Le Wi-Fi bloque toute une salle (fort impact), alors que l'installation logicielle ne gêne qu'un seul utilisateur.

    \item[\textbf{Q3 -- Pourquoi ajouter un suivi technique dans un ticket ?}]~\\
    Il trace chaque action effectuée, facilite la collaboration entre techniciens et sert de référence pour les incidents similaires.

    \item[\textbf{Q4 -- Risque de clôturer sans solution détaillée ?}]~\\
    Si l'incident se reproduit, le technicien repart de zéro faute de documentation, et l'utilisateur ne sait pas quoi faire pour éviter une récidive.
\end{description}
\end{qabox}

\section{Exercice 5 -- Base de connaissances}

\subsection{Article rédigé}

À partir du Ticket 3, j'ai rédigé l'article de base de connaissances suivant dans \textit{Outils > Base de connaissances}.

\vspace{0.6em}
\noindent\textbf{Titre de l'article :} \textit{Que faire lorsqu'un utilisateur ne peut plus ouvrir sa session Windows ?}

\vspace{0.5em}
\noindent\textbf{Problème rencontré :}\\
L'utilisateur ne peut pas se connecter à son poste Windows. Le message affiché est « Nom d'utilisateur ou mot de passe incorrect ».

\vspace{0.5em}
\noindent\textbf{Symptômes observables :}
\begin{itemize}
    \item Impossible de valider les identifiants sur l'écran de connexion.
    \item Message d'erreur au moment de la validation.
    \item Le problème persiste après redémarrage du poste.
\end{itemize}

\vspace{0.5em}
\noindent\textbf{Procédure de résolution :}
\begin{enumerate}
    \item Vérifier que la touche Verr.\ Maj n'est pas activée.
    \item Vérifier que la disposition du clavier est correcte (FR, pas EN).
    \item Tester la connexion sur un autre poste pour isoler le problème.
    \item Si l'échec persiste, contacter le technicien pour réinitialiser le mot de passe.
    \item Après réinitialisation, demander à l'utilisateur de changer son mot de passe à la première connexion.
    \item Documenter l'intervention dans GLPI et clôturer le ticket.
\end{enumerate}

\vspace{0.5em}
\noindent\textbf{Vérifications finales :}\\
S'assurer que l'utilisateur peut se connecter normalement et accéder à ses fichiers sans erreur.

\vspace{0.5em}
\noindent\textbf{Remarque de prévention :}\\
Inviter les utilisateurs à noter leurs identifiants dans un gestionnaire de mots de passe sécurisé pour éviter ce type d'incident.

\begin{qabox}
\begin{description}
    \item[\textbf{Q1 -- Comment la base de connaissances réduit-elle le nombre de tickets ?}]~\\
    Un utilisateur peut résoudre seul un problème déjà documenté, sans contacter le support, ce qui libère du temps aux techniciens.

    \item[\textbf{Q2 -- Différence entre suivi technique interne et article visible par les utilisateurs ?}]~\\
    Le suivi technique contient des informations sensibles réservées aux techniciens ; l'article de la base de connaissances est rédigé en langage simple, sans données confidentielles.

    \item[\textbf{Q3 -- Pourquoi rédiger une procédure simple et compréhensible ?}]~\\
    Une procédure trop technique ne sera pas suivie par un non-spécialiste ; des étapes numérotées et un vocabulaire accessible garantissent son application.
\end{description}
\end{qabox}

\section{Exercice 6 -- Analyse du fonctionnement du helpdesk}

La mise en place d'un outil de ticketing comme GLPI représente un changement structurant pour une organisation. Par rapport à une gestion par mail ou par téléphone, GLPI apporte une centralisation complète des demandes : chaque incident ou demande est formalisé, traçable et consultable à tout moment par les personnes concernées. Plus aucune demande ne peut être oubliée dans une boîte mail ou perdue dans un couloir.

Pour qu'un ticket soit réellement exploitable, il doit contenir a minima un titre explicite, une description précise du problème, un type (incident ou demande), une catégorie, une urgence, un impact, une priorité et le nom du requérant. Sans ces informations, le technicien ne peut pas agir efficacement.

Une mauvaise catégorisation des tickets entraîne des problèmes concrets : difficulté à assigner les tickets aux bons techniciens, statistiques faussées, et impossibilité de détecter les incidents récurrents par domaine. Si les tickets sont mal triés, l'équipe ne peut pas anticiper les besoins ni améliorer les procédures.

L'historique des tickets est une ressource précieuse. Il permet d'identifier les pannes récurrentes, de mesurer les délais de traitement, d'évaluer la charge de travail de chaque technicien et de justifier des demandes d'investissement matériel ou logiciel auprès de la direction.

Enfin, pour utiliser GLPI dans un vrai établissement, plusieurs précautions sont indispensables : activer le chiffrement HTTPS, appliquer une politique de mots de passe robuste, mettre en place des sauvegardes régulières de la base de données, gérer les droits d'accès avec rigueur, et sensibiliser les utilisateurs à l'outil pour en garantir l'adoption.
